# RCA — conex-assist-2: CRM login fails / app unreachable at Cloudflare edge (HTTP 520 "App not available")

## Symptom reported
Users cannot log in to the CRM. `POST /api/auth/login` from `/crm/login` shows the generic frontend error "Ocorreu um erro. Tente novamente." — which the frontend only renders when the request returns no usable HTTP/JSON detail (network error / non-JSON / 5xx / routing failure). Works in preview.

## What I verified (evidence)
1. **Edge returns 520 for EVERY path, not just login.** `preview_health_check` on the default domain `https://conex-assist-2.emergent.host`:
   - `GET /`          → **520**, body `"App not available"`, `content-type text/plain` (Cloudflare worker error)
   - `GET /api/`      → **520 "App not available"**
   - `GET /api/health`→ **520 "App not available"**
   This is a Cloudflare-layer error string, returned fast (32–317 ms), i.e. the edge/worker is not serving this deployment — static R2 content AND the `/api` proxy both fail identically.

2. **Backend is healthy.** `get_pod_events` (run 6e9e340b): pod `Running`, `ready:true`, `restart_count:0`. One early `Startup probe failed: statuscode 503` during boot, then recovered. `fetch_app_logs`: uvicorn alive, serving the in-pod `/health` probe (nginx converts backend 404→200 for `location = /health`, which is why readiness passes). **No public `/api/*` request ever appears in backend logs** → confirms edge requests never reach the origin.

3. **DB + seed are fine.** `mongo_query` on `users`: super admin `garciafinancas0073040@proton.me` exists with `role: super_admin`. 10 collections present. Seeding worked.

4. **Secrets all present & non-empty** (`list_secrets`, active run): `JWT_SECRET`, `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD`, `TURN_URLS`, `TURN_USERNAME`, `TURN_CREDENTIAL`, plus system keys (`MONGO_URL`, `DB_NAME`, `REACT_APP_BACKEND_URL`, `CORS_ORIGINS`, etc.). None empty.

5. **Frontend artifacts uploaded to R2 cleanly** (`get_build_logs`): `index.html`, `static/js/main.f8cf48c1.js`, CSS, metadata all copied to `deployer-frontend-artifacts/conex-assist-2/<run>/build/`. `[FRONTEND_BUILD] Build completed successfully!`

6. **All pipeline steps green** on both the initial run (6e9e340b) and the redeploy I performed (02b3a6b6): wakeup/build/mongo/secrets/deploy/health_check all `success`, promote committed (`active_run_id` = new run). Note the pipeline's `health_check` for a cloudflare frontend hits the pods' Service directly and **skips `GET /`**, so it never exercises the edge worker — which is why the pipeline reports success while the edge is broken.

7. **Redeploy did NOT fix it.** At the user's request I ran a full redeploy (run `02b3a6b6`, new image `...cf3685c`, cluster `deployment-cluster-09`, promoted successfully). Re-probing the default domain still returns **520 "App not available"** on `/` and `/api/health`. Two fully-promoted deploys both leave the app unreachable at the edge.

8. No custom domains attached (`list_domains` → empty); this is the platform **default** `emergent.host` hostname, which by design needs no DNS and should always resolve/serve.

## Root cause
Platform / Cloudflare edge routing defect. The Cloudflare worker that maps `conex-assist-2.emergent.host` → (R2 static + `/api` proxy to the k8s backend) is returning Cloudflare **520 "App not available"** for the whole deployment, even though every component behind it is healthy (backend pod ready, DB seeded, secrets set, R2 artifacts uploaded) and the deploy pipeline is fully green and promoted. The login failure and the generic frontend error are downstream symptoms of this edge failure (the browser gets a 520/non-JSON response, not a real 401/200). This is NOT a source-code, secret, DB, or tier problem, and it is not fixed by redeploying.
